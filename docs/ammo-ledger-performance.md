# 実包管理帳簿の操作性能と残数計算の改善

## 背景・解決したい問題

調査起点は main `feefd7a3f3ac2cc2bc1546ca610c9e0a101fc931`。消費登録などは保存成功後に全帳簿の再取得を待ってから遷移する。読取にも Server Action を使用しているため、読取と書込がクライアントの Action キューで直列化される。ロック設定には通信例外時に pending を解除しない経路があり、ロック成功後の SWR 状態同期もない。

## やること / やらないこと

- 読取を認証付き GET に移し、保存完了後の遷移と再取得を並行する。
- クライアントで完結する帳簿・残弾・ホーム間の遷移は Native History API に統一し、検索条件と戻る・進むを保持する。
- 初回データの重複取得、印刷時の重複取得、印刷前の不要な workspace 先読みを削減する。
- 通信失敗を表示して再試行可能にし、保存・ロック操作の処理中表示を必ず解除する。
- 独立したマスタ取得を並列化し、一括登録の INSERT をテーブルごとにまとめる。
- 用途別・年度別の繰越を保持して残数を計算し、残弾・棚卸し・編集・申請書の初期在庫を揃える。0発の繰越も保存できるようにする。
- DB スキーマ・認可ルールを維持し、過去データを一括書換えしない。Next.js 16.2.7 の既存機能で原因を解消する。

## 変更箇所

- `src/features/ammo-ledger/workspace/`: SWR、読取経路、初期データ、エラー表示。
- `src/features/ammo-ledger/navigation/` と `components/*-form/`: 保存後の遷移と異常系。
- `components/ledger-print-controls/`、`ledger/lock/`、印刷 page と documents: ロック・印刷の完了状態と取得回数。
- `transactions/prepare-confirmed-transaction/`、`create-bulk-transactions/`、`check-stock-before-save/`: DB 往復の削減。
- `catalog/` と `src/app/api/ammo-ledger/`: 一覧の読取 GET 化、最近使った相手先の JOIN。
- `src/sw.ts` と `src/app/serwist/[path]/route.ts`: 認証付きページと API の端末キャッシュを禁止。
- `ledger/compute-stock/`、`compute-running-home-stock/`、`opening-balance/`: 在庫計算と年初繰越の保存契約。

## 実装ステップ

1. 修正前の独立チェックアウトと専用ローカル PostgreSQL を用意し、架空データで操作を確認する。
2. 読取・遷移の共通経路を修正し、保存後のデータ表示と認証境界を検証する。
3. ロック・印刷とサーバー処理を修正し、既存の残数・ロック・並び順の契約を検証する。
4. 型・静的検証・関連テスト・production build・デスクトップとモバイルのブラウザ検証を行う。
5. 残数不一致の修正を最新mainへ統合し、再現テスト・独立レビュー後にPRを作成してマージする。

## 影響範囲とリスク

High: 非同期状態と DB transaction に関わる。保存済みなのに再取得失敗を保存失敗として表示しないこと、ロック確定前に公式印刷しないこと、別利用者のデータを返さないことを維持する。ロールバックはこの変更の revert。導入後は保存応答時間、workspace GET のエラー率、ロック操作失敗率、公式印刷の内容を確認する。

## 検証方法

遅延・失敗する HTTP 境界を使い、保存後に再取得を待たず帳簿を開けること、通信失敗後に再操作できることを検証する。実 DB で消費・一括登録・ロック・解除・残数拒否を確認する。既存 Unit/Component、typecheck、Biome、production build を実行する。計画自己レビューは GO: 根拠のある待機・重複取得を対象とし、migration と認可変更を含まない。

参考: [Next.js の読取と Server Functions](https://nextjs.org/docs/app/guides/backend-for-frontend)、[Native History API](https://nextjs.org/docs/app/getting-started/linking-and-navigating#native-history-api)、[Server Action 内の refresh](https://nextjs.org/docs/app/api-reference/functions/refresh)。

## 残る確認事項

- 本番DBのネットワーク遅延、クエリ実行計画、実際のINDEX、データ件数は未確認。schema/migrationsには帳簿のuser/date等のINDEXがなく、大規模化した際の追加候補となる。今回migrationは作成・適用していない。
- workspaceは依然として全履歴を取得し、帳簿画面も全行を描画する。年単位取得・ページ分割は繰越と表示仕様の検討を伴うため、この変更には含めない。
- 保存完了後の応答だけを失うケースは、再取得して保存状況を確認する案内を出す。冪等性キーによる二重登録防止は追加していない。
- 過去に0として入力されたが未保存となった繰越は、空欄との区別がDBに残っていないため自動補完しない。該当年・用途の年初繰越で0を再保存すると修正後の契約が適用される。
- 過去に元旦の通常取引より後へ記録された年初繰越のdayOrderは一括変更しない。年初繰越の再保存時に通常取引より前の順序へ修正される。
- 印刷ダイアログはテストで置き換える。実プリンター・PDFの出力結果と本番環境の体感は未検証。
